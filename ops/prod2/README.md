# prod2 logging and encrypted MySQL backups

These files implement approved specification `prod2-logging-mysql-drive-backup-20261102` v1 (SHA-256 `4F9576BF8112C0E1CD58776A9CD6DF3196576414BC702FB9033156ED307E66AF`). Installation, account creation, container replacement, OAuth consent, enabling timers, and production deployment require the separate production approval. This package never touches prod1 or the live MySQL data directory.

## Prerequisites and installation

On prod2 verify free disk and Drive quota against **seven daily compressed dumps plus logs per week**, including 14 days local and 56 days remote; current logical data was roughly 7.3 GB before compression. Staging temporarily duplicates all eligible files. Configure alerts for free disk, timer failures, stale dump/upload, quota, and OAuth failures in the existing operational monitoring; inspect with `systemctl --failed`, `systemctl list-timers 'memonogi-*'` and `journalctl -u memonogi-db-backup -u memonogi-drive-upload` until monitoring is available. Neither timer provides notifications itself.

Prerequisites: Ubuntu 24.04, `node` 20+ at `/usr/bin/node`, Docker Compose v2, `rsyslog`, `logrotate`, `util-linux` (`flock`), and rclone installed from an authenticated official release. The network `infra_devnogi-network` and healthy `devnogi-mysql:3316` must already exist. Install the reviewed repo revision on prod2, then as root run `sh ops/prod2/install.sh`. It installs settings, validates syntax, and reloads systemd, but does **not** enable or start timers or restart rsyslog. Existing `/etc/memonogi-backup` secrets are untouched. Review `rsyslogd -N1` and `logrotate -d /etc/logrotate.d/memonogi`, then restart rsyslog with `systemctl restart rsyslog` and confirm it is active. Re-running the installer replaces only the named package files; re-run those validations after upgrades. Do not enable either timer at this stage.

Five fixed syslog tags route to `/var/log/memonogi/{auth,community,batch,gateway,react}/application.log`, owned by `syslog:adm`. Rotation runs daily, compresses closed files, and retains them until verified weekly upload and age greater than 14 days. During failure, files deliberately accumulate; watch disk capacity. Default Ubuntu logrotate scheduling determines the exact rotation time. Neither Docker's internal JSON files nor active files are copied by the weekly uploader. Gateway/Batch's existing application log volumes remain intact and are not uploaded a second time.

Before each approved app recreation, preserve its current `docker logs --timestamps` output in its service directory under `pre-transition-YYYYMMDDTHHMMSSZ.log.gz`, as root with umask 077, then confirm `gzip -t`. Stop if capture fails. Recreate just that service using its approved deployment workflow; confirm its health and a new message in its own host file and check `docker logs`. Repeat for the remaining apps. Verify no cross-routing, simulate daily logrotate with a test fixture, check rsyslog restart recovery, and inspect file modes. Rollback is the previous app Compose logging configuration and image, followed by health checks; never remove app log volumes.

## Backup account and dump

Create a dedicated MySQL account from an interactive, authenticated administrative session, avoiding shell arguments, history, logs, and CI output for its generated password (e.g. set `MYSQL_HISTFILE=/dev/null` before starting the MySQL client). Restrict the account's host to the actual Docker network/client range where feasible. Grant `SELECT, SHOW VIEW, TRIGGER, EVENT` on each of `auth`.*, `dcs`.*, and `open-api-batch`.* and the global `SHOW_ROUTINE` privilege so routine definitions can be read. Verify these exact grants and an actual dump and restore against an isolated MySQL 8.0.42 instance first; do not broaden permissions silently. MySQL's [privilege documentation](https://dev.mysql.com/doc/refman/8.0/en/privileges-provided.html) describes the global routine-definition visibility granted by `SHOW_ROUTINE`. If the tested version requires more, stop and review the narrower available option before changing production privileges.

Create `/etc/memonogi-backup/mysql.cnf`, root:root mode 0600, containing a `[client]` section with `user` and `password` for that account; create it interactively without echoing its contents. Never commit or print it. The backup client mounts this file read-only and connects over the external Docker network. Check all target tables are InnoDB; coordinate Flyway/DDL to avoid the snapshot window, since `--single-transaction` cannot protect against concurrent DDL or nontransactional tables. The dump targets exactly the three schemas, writes `.partial`, validates the gzip stream and schema markers, writes SHA-256, then atomically promotes the dump. Inspect failed service logs without revealing data or credentials. If setup is rolled back, disable timers and revoke the dedicated account only after verifying its exact identity.

After account setup manually start `systemctl start memonogi-db-backup.service`. Verify a nonempty `.sql.gz` and its matching `.sha256`, `gzip -t`, and `sha256sum -c` from the backup directory. Restore a copy into a **separate isolated** MySQL 8.0.42 instance with synthetic credentials and no production volumes or network access; check the three schema names, representative table counts, and any views, routines, events and triggers. Do not run a restore against prod2. Record the restore evidence and durations. Repeat isolated restore periodically and after schema or MySQL changes.

## Google Drive and weekly upload

Use the user's own Google OAuth account and rclone's `drive.file` scope; a service account is not a substitute for personal My Drive storage. Configure `gdrive` to create its private `Memonogi-Backups` folder and `memonogi_crypt` with remote `gdrive:Memonogi-Backups/prod2`, filename encryption `standard`, and directory name encryption `true`. Follow the [rclone Drive](https://rclone.org/drive/) and [headless authorization](https://rclone.org/remote_setup/) instructions. The Google account owner must perform interactive consent; a client in Google OAuth Testing may have short-lived refresh tokens. Store `/etc/memonogi-backup/rclone.conf` root:root mode 0600; record crypt password and salt outside prod2 in the owner's password manager. The program checks remote type, scope, encryption, and exact destination before upload or deletion. The remote root must be dedicated to this backup: pruning is permanent.

Before enabling the timer, use a separate synthetic test folder and `rclone copy --dry-run`; upload, decrypt and download a synthetic file, then upload a real completed dump using the service and verify with `rclone cryptcheck --one-way`. Download/decrypt the dump, verify its checksum, and repeat the isolated restore above. Test expired credentials/network failure and confirm no local cleanup occurs. Successful runs stage only complete dumps and checksums plus compressed rotated/pre-transition logs, verify their checksums and cryptcheck, and record a local verified manifest. Only unchanged verified source files older than 14 days are removed. After a successful copy and cryptcheck, objects older than 56 days are permanently deleted only within the dedicated crypt remote; account-wide `rclone cleanup` is never used. Remote pruning is deferred if an over-56-day local file is uploaded in that run. Partial failures during a remote delete can remove some already-expired remote objects; remaining local sources are retained and the failure is reported.

Finally, after every acceptance check passes, `systemctl enable --now memonogi-db-backup.timer memonogi-drive-upload.timer` and inspect `systemctl list-timers 'memonogi-*'`. Schedules are 05:30 KST daily and 06:30 KST Sunday; persistent timers catch up once after downtime, not for every missed day. Normal loss exposure is approximately 24 hours for local disk and up to a week for off-host Drive. To pause, disable/stop the two timers and leave data, credentials, and volumes intact; restore a prior rsyslog config and restart rsyslog only after apps are reverted.
